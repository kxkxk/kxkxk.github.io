FoundationDB 的事务有三个容易混在一起的时间点：**读取哪个版本、并发检查是否通过、修改是否已经持久化。** 把这三件事分开，才能解释为什么两个事务写不同的 key 也会冲突，为什么 Resolver 可以只保存近期历史，以及为什么 StorageServer 尚未落盘时，客户端就能收到提交成功。

本文以 SIGMOD 2021 的 [《FoundationDB: A Distributed Unbundled Transactional Key Value Store》](https://www.foundationdb.org/files/fdb-paper.pdf)为主线，页码均为这份 14 页 PDF 的页码。使用论文的 Sequencer、Proxy、Resolver、LogServer、StorageServer 名称；较新的文档将 Proxy 拆为 GRV Proxy 与 Commit Proxy，并使用 Master 等名称。**论文中的 SQLite 存储引擎和实现细节只代表论文所述版本，不直接视为当前所有部署的配置。** [官方架构文档](https://apple.github.io/foundationdb/architecture.html)

文中区分三类内容：**论文机制**来自原文；**教学推导**用简化例子解释机制，不宣称等同源码实现；**外部比较**依据 TiKV/TiDB 官方资料，不属于 FDB 论文的实验结论。外部文档核对日期为 2026-11-06；`stable`、`dev` 页面会继续更新，部署时应切换到对应产品版本。

## 一笔事务的完整路径

FDB 提供有序 KV 接口和跨 key 事务。MVCC 让事务在同一个版本上读取；OCC 在提交时检查这些读取依赖是否仍然有效。默认事务具有严格可串行化语义：并发执行的效果可以按某个串行顺序解释，而且该顺序尊重真实时间上已经完成的事务与随后才开始的事务。［论文 §1、§2.4］

先记住五个角色：

| 角色 | 核心职责 |
|---|---|
| Sequencer | 提供读版本与提交版本，建立版本顺序 |
| Proxy | 接收客户端提交，组织冲突检查与日志持久化 |
| Resolver | 验证读冲突范围，维护近期写冲突历史 |
| LogServer | 保存按策略复制的事务日志 |
| StorageServer | 管理键范围、保留 MVCC 数据并服务读取 |

一笔普通读写事务可以按下面的路径理解：

```text
Client 获取读版本 r
    │
    ├─ 向 StorageServer 读取版本 r 的数据
    └─ 在客户端暂存 mutation，记录读写冲突范围
              │
              ▼
Proxy 取得提交版本 c
              │
              ▼
相关 Resolver 检查冲突
    │ 不通过：中止，由客户端决定是否重试
    ▼ 通过
指定 LogServer 日志副本完成持久化
              │
              ▼
Proxy 向 Sequencer 报告已提交版本
              │
              ▼
Proxy 向客户端确认提交成功

LogServer ── 后台日志传送 ──> StorageServer 应用更新与批量落盘
```

**提交成功不等待 StorageServer 将数据写入本地数据文件。** 提交阶段的持久性由日志系统承担。与此同时，客户端写缓存提供读己之写语义，事务不需要先把自己的修改发送到存储节点，再读回来。［论文 §2.2、§2.4.1、§2.4.3，PDF 第 3–5 页］

论文还明确给出一个顺序：指定日志副本确认后，Proxy 先向 Sequencer 报告已提交版本，再向客户端回复成功。这让随后开始的事务取得的读版本不早于这次已经完成的提交，是将版本排序与严格可串行化的真实时间要求连接起来的一步。［论文 §2.4.1，PDF 第 4 页］

如果一个 StorageServer 还没追到请求的读版本，读取需要等待、尝试其他副本，或以可重试错误结束。它不能把旧值当作所请求版本的结果返回。因此，**存储层异步追赶日志，与事务读取可以任意陈旧，是两回事。** ［论文 §2.4.3］

## 冲突检测检查什么

### 用近期写入验证读取依赖

Resolver 不需要重新读取业务 value，也不比较两次 value 是否相同。它使用事务的读版本、读冲突范围、写冲突范围，以及近期写入历史。

论文 Algorithm 1 的核心条件是：对于事务的某个读冲突范围，如果存在相交的历史写入，其版本大于本事务读版本，则中止。简化表示为：

```text
存在相交的读范围与历史写范围，且
历史写版本 > 本事务 readVersion
    => 当前事务冲突
```

检查按提交顺序进行，所以这里查的是当前事务之前已处理的写入。通过本地检查后，Resolver 将当前事务的写冲突范围及提交版本登记到历史中。**本地放行还不是持久化提交完成。** ［论文 §2.4.2、Algorithm 1，PDF 第 4–5 页］

用一个教学例子区分三个版本：

```text
T1、T2 都在读版本 100 读到 A = 50
T1：计算 A - 10，在提交版本 120 被接受并提交
T2：也计算出了 A = 40，拿到提交版本 130

T2 检查时：
lastCommit[A] = 120 > readVersion(T2) = 100
因此 T2 中止
```

`130` 再新，也不能让 T2 之前读到的 `A = 50` 自动变成 `40`。重试必须重新读取和计算，不能只给旧的计算结果换一个提交版本。

反过来，如果 T1 只写 B，而 T2 只读写 A，且没有其他依赖，T1 的修改就不会使 T2 发生这类冲突。**判断的是读取依据是否被改动，而不是数据库中是否发生过任意更新。**

### 写写重叠不等于必然冲突

下面三种情况要分开：

| 事务关系 | 在这个简化场景下的结果 |
|---|---|
| T1、T2 都先读 A，再写 A | 后处理者可能因 A 的读取依赖失效而中止 |
| T1、T2 都不读旧值，只 `set(A, ...)` | 两次盲写可以都提交，按事务顺序解释最终值 |
| T1、T2 都读 A、B，分别只写 A 和 B | 即使写的 key 不同，后处理者仍可能冲突 |

第二行假设没有额外读冲突范围或其他业务依赖。两次盲写可以提交，并不表示两次业务更新都被保留下来；后面的覆盖前面的，是这种数据操作本身的含义。

这些结果都可由 Algorithm 1 推出，官方开发文档也明确区分读写冲突与写写冲突。[FDB 冲突范围说明](https://apple.github.io/foundationdb/developer-guide.html#conflict-ranges)

### 范围读保护尚不存在的 key

假设事务在版本 100 完整读取 `[k100, k200)`，得到 `k120`、`k180`，然后准备把条目数 `2` 写入另一个 key。另一个事务在版本 120 插入 `k150`。

如果只检查当时返回的两个 key，就会漏掉这次插入。记录读取范围后，新写入的 `k150` 与该范围相交，汇总事务便会被中止。这是论文所述防止幻读的机制。［论文 §2.4.2］

这里使用的是完整范围读取的教学例子。实际 API 的 limit、方向、迭代消费情况和显式冲突范围都会影响事务依赖，不应把“调用了一个范围 API”直接等同于“所有传入边界之间的 key 一律参与冲突”。

## Resolver 的区间历史

### 历史按版本窗口过期

论文把 `lastCommit` 描述为“键范围到最近提交版本”的映射，实际使用 **带版本信息的概率 SkipList**。它保留近期写入历史，修改记录在 MVCC 窗口之外过期；论文中的窗口是约 5 秒。［论文 §2.4.2，PDF 第 4–5 页］

这不是一个可以随意丢弃冷 key 的缓存。如果某个范围的修改仍可能使合法事务的读取失效，即使这个范围最近只写过一次，也不能因为它不热门而忘掉。

教学上，可以这样理解安全淘汰条件：设系统不再接受小于某个最低读版本的事务，那么早于该边界的写入就不再需要参与这些事务的冲突判断。**历史保留与事务可使用的旧版本范围必须配套。** 这是对窗口机制的解释，不是对某个源码清理函数的逐行描述。

“只保留几秒”也不等于内存大小固定。在相同窗口内写入更多不同范围，历史结构仍可能变大。把过期记录清掉与控制当前工作负载，是不同的问题。

### 一个可推演的区间模型

下面是教学模型，假设历史被表示为有序、互不重叠的分段，每段记录最近写版本：

```text
[a, d) -> 90
[d, h) -> 110
[h, m) -> 95
```

一个读版本为 100 的事务读取 `[c, j)`：

1. 定位到包含 c 的段 `[a, d)`，检查版本 90。
2. 检查 `[d, h)`，发现 `110 > 100`，即可判定冲突。
3. 不需要为了得到“有冲突”这个答案，继续枚举后面的段。

如果之后某次被接受的写入覆盖 `[f, k)`，版本为 120，概念上的更新结果是：

```text
[a, d) -> 90
[d, f) -> 110
[f, k) -> 120
[k, m) -> 95
```

过程包括在边界拆段、覆盖内部区域，以及在适用时合并相邻等价段。这里解释的是一种区间映射的语义，**论文没有给出这套完整的拆段、合并实现，不能把示意图当作 FDB 内存布局。**

### 区间求交与复杂度的边界

设教学结构中保留了 n 个区间，某次查询与 k 个区间相交。采用标准有序查找并顺序遍历时：

- 期望定位成本为 `O(log n)`，这里使用 SkipList 的期望查找性质。
- 枚举相交区间需要 `O(k)`。
- 因而这个模型的区间枚举成本为 **期望 `O(log n + k)`**。

如果事务有多个读范围，还需考虑每个范围的定位、访问总量，以及区间之间的重叠。写范围更新也不是统一的 `O(log n)`：要计算边界操作、被覆盖节点的处理和维护成本。逐节点删除与批量摘除链段，会有不同的成本。

**以上是算法推导，不是论文承诺的 Resolver 复杂度。** 论文给出 Algorithm 1、版本增强 SkipList 和一个限定工作负载的微基准，却没有证明所有查询或更新的渐进界限。增强结构可能跳过一整段不会冲突的历史；查询只求“是否存在冲突”，也可能提前退出。因此，不能把 `O(log n + k)` 写成实际实现每次都必须访问 k 个区间，更不能把微基准吞吐换成线上性能保证。［论文 §2.4.2］

### 多个 Resolver 与保守中止

整个键空间分给多个 Resolver，事务涉及的所有 Resolver 都要同意。某个 Resolver 已登记写范围，但另一个 Resolver 随后否决整笔事务时，前者留下的记录可能让后续事务产生不必要的冲突。

论文明确提到这种 **false positive**。它会造成保守中止，而不是放过本来不安全的事务；相关历史的影响受 MVCC 窗口限制。所以，把 `lastCommit` 理解成“每一条都对应已经向客户端确认成功的提交”，也过于严格。［论文 §2.4.2］

## 日志与存储的持久化

### 两条路径，各自负责什么

| 阶段 | 作用 | 客户端提交是否等待 |
|---|---|---|
| Resolver 验证 | 决定是否接受当前读取依赖与修改 | 等待相关检查结果 |
| LogServer 持久化 | 让修改日志满足指定的复制持久性条件 | 等待指定日志副本确认 |
| StorageServer 接收并应用 | 形成可按版本读取的数据 | 不在提交确认关键路径上 |
| StorageServer 本地数据文件落盘 | 批量整理查询数据，推进存储持久化进度 | 不在提交确认关键路径上 |

论文要求所有**指定的**日志副本完成持久化。不能把它改写成“所有 LogServer 都保存该事务全文”，也不能直接套用“Raft 多数派确认”的说法。论文把日志复制与控制面 Coordinators 的 Paxos 分开描述。［论文 §2.4.1、§2.4.3、§2.5］

### 没有 mutation 的 LogServer 仍会收到消息

论文图 2 中，Proxy 根据修改所属的存储分片添加 StorageServer tag，将 mutation 正文发给选中的 LogServer，并满足日志复制要求。其他 LogServer 收到空正文消息。

消息头携带 LSN、previous LSN 和 Proxy 的 KCV。**正文决定该节点保存什么数据，顺序信息帮助节点知道日志流推进到哪里。** 版本值不必连续相差 1，previous LSN 用于连接实际的处理顺序。［论文 §2.4.2–2.4.3，PDF 第 4–5 页］

不要因为一台节点收到空正文，就推出它保存了这笔事务的完整副本；也不要因为它收到了消息，就推出客户端确认时它一定已完成相应持久化。

### StorageServer 可以先接收，再批量落盘

论文中的 StorageServer 会积极拉取日志，甚至可以在日志系统完成持久化之前拿到更新。近期多版本更新暂存在内存，数据文件写入则更晚进行，可以合并多次更新、提高 I/O 效率。

因此，需要区分：

```text
StorageServer 已收到更新
    ≠ 客户端已收到提交成功
    ≠ 更新已进入 StorageServer 的本地 B-tree
```

论文所述存储引擎由无版本 SQLite B-tree 与内存多版本更新组成，只把离开 MVCC 窗口的已提交更新写入 SQLite。故障恢复确定保留边界后，可以丢弃超出边界的内存版本。**这些是论文版本的实现细节，不能推广成所有新存储引擎的内部实现。** ［论文 §2.4.3–2.4.4，PDF 第 5–6 页］

日志也不是永久保留。官方架构文档补充说明：StorageServer 将更新持久化后，会通过 pop 推进相应日志的释放进度，让日志系统回收不再需要的部分。这个生命周期是“日志先保证提交持久性，存储随后持久化，再推进日志释放”，不能在客户端一收到成功时就删除所需日志；存储节点落后或故障时，待它消费的日志还可能积压。[官方事务日志说明](https://apple.github.io/foundationdb/architecture.html#transaction-logs)

### 恢复边界中的 KCV、DV、PEV 与 RV

论文 §2.4.4 给出四个量：

- **KCV（Known Committed Version）**：Proxy 已知的提交进度，会随之后的日志消息捎带给 LogServer。
- **DV（Durable Version）**：LogServer 自身已持久化的日志版本进度。
- **PEV**：恢复阶段依据收集到的 KCV 得到的前一 epoch 的已知提交边界。
- **RV（Recovery Version）**：恢复阶段选取的日志保留边界。

论文先停止旧 LogServer 接受事务，再从满足恢复条件的回复集合中，用最大 KCV 确定 PEV，用最小 DV 确定 RV；将需要接续的 `(PEV, RV]` 日志补到新日志系统，通知存储层丢弃 RV 之后的旧状态。这些最大值、最小值针对的是协议收集的旧日志节点回复，不能任取几个运行中节点的指标来计算。**KCV 可能滞后，因此 PEV 不能简单等同于所有客户端已收到成功的精确最高版本。**

论文还给出一个副本覆盖条件：旧系统有 m 个 LogServer，每条日志有 k 份副本，收到超过 `m-k` 个回复，就能与任意 k 副本集合至少相交一次。教学上，这是因为未回复的节点少于 k 个，不可能把某条日志的全部副本都藏在未回复集合中。

这个集合推导只证明“至少能遇到一份正文副本”。**完整恢复安全性还依赖日志顺序、停止旧系统、版本边界和复制协议，不能只靠这一个不等式证明。** 同样，不能从“指定数据副本已回复”直接推出“全部 LogServer 的 DV 都已超过该提交版本”。在配置承诺的故障容忍范围内，已向客户端确认成功的事务必须被保留；这些简化公式不能脱离协议，作为独立、完整的恢复算法。

从架构角度，更重要的结论是：恢复先确定安全的日志边界，StorageServer 沿正常后台路径继续应用日志。新事务系统不必等所有旧日志都重放到存储数据文件，才能重新接受工作。［论文 §2.4.4］

## 频繁重试与冲突粒度

### 冲突粒度由 key 与冲突范围表达

FDB 的 value 是字节串。文件、目录、inode 或 JSON 字段，都是上层映射到 KV 的数据模型；FDB 不会自动把一个 value 拆成字段级冲突单元。[官方数据建模文档](https://apple.github.io/foundationdb/data-modeling.html)

下面是文件系统元数据的教学设计，不代表某个具体文件系统的实际编码：

| 数据组织 | 可能产生的竞争 |
|---|---|
| `inode/100 -> {size, mtime, mode}` | 普通读后改写整条记录时，不同字段的更新也依赖同一个 key |
| `inode/100/size`、`inode/100/mode` | 若业务约束独立且没有其他交叉读取，可以缩小冲突范围 |
| `extent/100/0`、`extent/100/1` | 不同块映射可分别更新，但文件长度等公共元数据仍可能成为依赖 |
| 创建不同文件，都读改 `dir/200/count` | 文件名不同，仍会竞争公共计数器 |

所以，不能用“是否同一个文件”判断冲突。把 key 拆细也不是无条件的优化：如果业务要求多个属性一起满足约束，事务仍必须读取并验证相应依赖。

### 四类常见重试来源

**1. 热点读改写。** 多个事务从同一版本读到 `count = 100`，都准备写 `101`。在没有其他干扰的这批尝试里，一个先通过后，其余尝试的读取依据就失效。重试后如果仍然一起争抢，竞争会继续。这是 OCC 的机制推演，不是一个实测吞吐结论。

**2. 大范围读取后写入。** 事务完整扫描目录，再据此更新统计或状态，期间目录内持续插入或删除，就容易与读范围相交。即使最终只写一个汇总 key，也不能只看这个写 key 是否热门。

**3. 事务持续时间过长。** 外部 RPC、大量计算或串行读取，会延长读取到提交的窗口。即使没有业务冲突，也可能因可用版本过旧而失败。官方已知限制仍描述从首次读取开始约 5 秒的限制；具体错误及缓存读取行为要按对应版本和绑定理解。[长事务限制](https://apple.github.io/foundationdb/known-limitations.html#long-running-transactions)

**4. 故障、恢复与提交结果不确定。** 存储落后或事务系统故障会造成重试，不能看到重试就认定是热点。`commit_unknown_result` 尤其要单独处理：客户端没收到确定结果，不等于修改一定没有生效。[未知提交结果](https://apple.github.io/foundationdb/developer-guide.html#transactions-with-unknown-results)

纯只读事务依靠 MVCC 快照，不会因为其他事务写入而发生同样的提交冲突；它仍可能遇到版本过旧等读取错误。把“读范围越大越易冲突”用于只读查询，会漏掉这个区别。［论文 §2.4.1］

### 优化从业务依赖开始

| 现象 | 可以考虑的改法 | 需要守住的边界 |
|---|---|---|
| 计数器反复读改写 | 语义允许时使用 atomic add | 若还需普通读取同一计数器，其读依赖仍可能产生冲突；原子操作不消除物理热点 |
| 所有请求都修改公共记录 | 拆分独立字段、分片计数或减少公共更新 | 总量读取和跨字段约束需要重新设计 |
| 扫描范围远大于实际决策需要 | 使用更窄的索引与读取范围 | 不能漏掉决定正确性的“没有其他记录”条件 |
| 事务中有外部等待 | 把可移出的计算与准备移到事务外 | 进入事务后仍需重新验证相关条件 |
| 高竞争下重试放大负载 | 使用绑定的错误处理与退避，限制热点并发 | 重试不是无限资源，也不保证某次尝试必然成功 |

Snapshot read 不记录普通读冲突范围，因此可能减少冲突，但必须证明剩余检查足够维护业务约束。把所有普通读改成 snapshot read，可能减少重试，却不能自动保证业务约束仍然成立。［论文 §2.4.1–2.4.2；[官方 snapshot read 说明](https://apple.github.io/foundationdb/developer-guide.html#snapshot-reads)］

重试循环还需要业务幂等性。常见做法是在循环外生成稳定请求 ID，在同一 FDB 事务中检查完成标记，再原子地写入业务修改和完成标记。数据库事务外的发送消息、扣款或调用其他服务，并不会自动获得这项保证。[官方幂等处理建议](https://apple.github.io/foundationdb/developer-guide.html#transactions-with-unknown-results)

## 论文中的优化

### 批处理版本分配、检查和日志写入

Proxy 将多个事务组成一批，向 Sequencer 获取一个提交版本，批量交给 Resolver，再把通过的事务写入日志。低负载减小批次以减少等待，高负载增大批次以摊薄固定开销。［论文 §2.6，PDF 第 7 页］

因此，统一版本顺序不意味着每笔事务的读取、计算和落盘都逐笔串行进行。也不能假设每个事务都有不同的提交版本：同一批次可以共享版本，批内仍需正确处理事务之间的冲突。

### 提交版本在冲突检查前分配

这使版本分配和冲突检查能够有效批处理。事务得到提交版本后仍可能被拒绝，提交版本不是成功凭证。［论文 §2.4.2］

### 原子操作减少读依赖

原子加法等操作由数据库执行变换，省去客户端读取旧值的往返，也避免这一步带来的读冲突依赖。论文还介绍了版本戳操作，可把提交版本写入 key 或 value 的一部分。［论文 §2.6］

减少的是原子操作本身的读依赖，不是免除整笔事务的所有冲突检查。同一事务中的普通读取仍可能带来冲突；若还普通读取了原子操作涉及的 key，就不能再假定该事务拥有纯原子更新的避冲突收益。[官方原子操作说明](https://apple.github.io/foundationdb/developer-guide.html#atomic-operations)

原子加法的意义是让“加一”作为变换参与排序，而不是把每个客户端算出的同一个新值重复覆盖。它不会让无限写负载在单个 key 上变得没有成本。

### 读、提交与落盘分别扩展

读取直接访问 StorageServer；提交经过 Proxy、Resolver 与 LogServer；存储数据文件异步批量更新。不同路径可以分别分配资源，但这不等于每种负载都能无限线性扩展。热点键、网络、磁盘、排队与事务依赖仍然存在。［论文 §2.3.3、§2.4.3］

论文的目标负载是读多、每笔事务涉及少量 key、冲突较低的 OLTP。评估这些优化时，应把这一前提一起带上。［论文 §2.3.2］

<a id="tikv"></a>

## 与 TiKV 比较：机制与适用前提

本节是外部比较。FDB 一列主要对应本文所述论文架构；TiKV 一列区分经典 Percolator 路径与后续优化，不代表任意版本、SDK、配置下都走同一条路径。

### 先对齐隔离语义

FDB 默认事务提供严格可串行化，TiKV Transactional API 以 Snapshot Isolation 为基础。仅凭两者都有 MVCC、全局时间戳和 ACID，不能认为隔离保证相同。FDB 的逐次 snapshot read 选项，也不能直接等同于“切换成与 TiKV 完全一样的事务模式”。[TiKV 事务 SIG 说明](https://tikv.org/blog/announcing-sig-txn/)

一个教学例子是：两名值班者都读到另一人在岗，然后分别把自己改为离岗。它们写不同 key，却共同依赖“至少一人在岗”。使用 FDB 普通读时，后处理者可由读写范围相交被拒绝；仅有 SI 的写写冲突检测，则不能一般性排除这种 write skew。实际业务可以通过锁、公共约束 key 等手段建立额外保护，比较时必须计入这些操作。

### 经典提交路径与 Region 复制

| 维度 | FDB：本文论文架构 | TiKV：经典事务路径 |
|---|---|---|
| 冲突处理 | 独立 Resolver 验证读范围与近期写历史 | prewrite 阶段围绕 key 的锁和 MVCC 写版本处理冲突 |
| 事务提交 | Proxy 组织检查，随后等待指定日志副本持久化 | Percolator 式 prewrite、commit，primary 参与决定提交状态 |
| 数据复制 | 日志同步持久化，存储副本后台追赶 | 每个 Region 的副本由该 Region 的 Raft group 复制 |
| 可查询数据的形成 | StorageServer 后台应用日志 | Raft 提交的操作再应用到本地 KV 存储 |
| 需要关注的成本 | 读版本、验证、日志持久化、热点和排队 | 事务协调、Region 路径、Raft 复制、锁与冲突 |

TiKV 的经典 Percolator 流程先 prewrite 相关 key，再提交 primary，随后完成 secondary 的提交。primary 已提交后，secondary 尚未完成清理，不意味着事务可以只生效一半。[TiKV Percolator](https://tikv.org/deep-dive/distributed-transaction/percolator/)

**Percolator 协调跨 key 的事务，Raft 解决 Region 副本的一致复制。** 这两个层次不能合并成“有 Raft 所以跨 Region 事务天然原子”，也不是每个事务临时建立一个 Raft group。[TiKV 存储架构](https://tikv.org/docs/dev/reference/architecture/storage/)

TiKV 同样要区分日志持久化、状态机应用和数据文件刷盘。“应用到本地 KV 存储”不等于“提交必须等待数据全部写成 SST 文件”。因此，不能把“日志与数据文件刷盘可以分离”描述成 FDB 独有的能力；本文比较的是系统角色拆分和事务协议路径。[TiKV 持久性说明](https://tikv.org/docs/6.5/reference/faq/)

### Async Commit 与 1PC 会改变前台路径

符合条件时，Async Commit 可在增强的 prewrite 完成后返回成功，将后续 commit 工作放到后台；这不等于省去持久化或复制。1PC 则适用于单 Region 等条件下的事务。启用某项能力只使它成为可选路径，并不意味着全部事务都会使用它。[Async Commit 设计](https://tikv.github.io/sig-transaction/design/async-commit/index.html)、[TiDB Async Commit 配置](https://docs.pingcap.com/tidb/stable/system-variables/#tidb_enable_async_commit-new-in-v500)、[TiDB 1PC 配置](https://docs.pingcap.com/tidb/stable/system-variables/#tidb_enable_1pc-new-in-v500)

这里的 Async Commit 设计页是历史设计资料，不能把其中的实现进度或早期阈值当作当前状态。TiDB 参数说明用于确认优化的适用条件，不能将其默认值直接套到裸 TiKV SDK。TiDB SQL 层的悲观事务模式，也不应与 TiKV Transactional API 的行为混写。

### 架构只能说明成本在哪里

从路径可以分析：FDB 把冲突验证集中到可分区的内存角色，把存储数据文件落盘移出提交确认路径；TiKV 的分析需要同时看实际提交协议、涉及的 Region 和 Raft 复制路径。

由此不能推出“FDB 一定更快”“TiKV 延迟是两倍”或“SI 一定更快”。尤其不能拿一个 Resolver 的微基准，对比另一个数据库的端到端事务吞吐。

真正比较时，至少应固定或明确：

- 产品和客户端版本、隔离语义，以及业务约束的实现方式。
- 事务大小、读写比例、热点程度和冲突率。
- FDB 的复制配置，TiKV 的 Region 分布和实际提交协议。
- 网络拓扑、故障域、磁盘与持久化配置。
- 统计的是成功事务还是总尝试，是否包含重试，以及尾延迟。

这份清单是评测方法建议，本文没有进行同条件性能测试。

## 小结

理解 FDB 可以抓住四条线：

1. **读版本决定读取视图，提交版本决定排序依据。** 拿到提交版本不等于成功。
2. **冲突检查保护读取依赖。** 最终写不同 key 也可能冲突，纯盲写相同 key 则不必然冲突。
3. **Resolver 保留的是有限窗口内的区间历史。** 淘汰依据是版本有效性，区间复杂度要区分教学模型与真实实现。
4. **日志持久化与查询数据落盘分工不同。** StorageServer 异步追赶，但读取仍受版本约束。

回到应用设计，最有价值的检查通常是：事务究竟依赖哪些条件，这些条件映射成哪些读冲突范围，是否把不必要的等待和公共热点放进了事务，以及重试是否会重复执行业务动作。
